One bug, start to finish

A real run of the bugfix pipeline on a WordPress theme. Every step is a fresh agent session that sees only its task and the code.

  1. Reproduce

    One session writes a test that fails because of the bug, and touches nothing else.

    The Metrics grid ignored its tablet and mobile column settings. New test: 203 pass, 2 fail.

  2. Fix

    A second session makes the failing test pass.

    Per-device columns wired through to the markup and CSS. All tests green.

  3. Score

    Two scorers on different models grade it without seeing each other. A third session reruns the checks and settles it.

    94 / 100, held back

    Over the bar, but one scorer caught a real defect: the tablet value was ignored between 783 and 1024 pixels.

  4. Fix again

    A new session gets only what the score reported.

    A simpler fix that uses Elementor's own breakpoints: 15 lines added, 34 removed.

  5. Score again

    New scorers, who never see the earlier score.

    97 / 100, ready

    Nothing left that must be fixed. The branch waits for a person's yes before it is merged.

How a change earns its score

Whoever wrote the change does not get to judge it. Two scorers that did not see it being built grade it against a fixed rubric, and every point needs evidence a person can check.

Requirements
30%
Tests
20%
Security
15%
Maintainability
15%
Operational
10%
Scope
10%
  • Ready means 90 or more, with nothing left to fix. A change that scores 94 with one serious finding open is not done.
  • Severity has fixed definitions. Critical means the change fails at its job, can be exploited or damages data. A finding is never rated by comparing it with the others in the same review.
  • The consensus checks for itself. It reruns the tests and opens every file and line a finding cites. What it cannot confirm is dropped.
  • The loop is bounded. It fixes only what the score reported, then stops at the target, on a plateau, or after a set number of rounds.

Ten pipelines

A pipeline is a short list of steps. Each step runs in its own session and its own git worktree, and ends in a report.

  • onboardwrites

    Gives a project its profile, with check commands that were actually run.

  • specwrites

    Drafts a spec with testable requirements, then has it challenged.

  • featurewrites

    Implements a brief, tests it, then verifies and fixes up to the target.

  • bugfixwrites

    Reproduces a bug with a failing test, fixes it, then scores the fix.

  • docswrites

    Finds docs that drifted from the code, fixes them, and audits again.

  • reviewreads

    Three focused audits and an independent score, on one page.

  • measurereads

    The score alone: two scorers and a verified consensus.

  • verifyreads

    Three audits and two scorers settled by one consensus. It closes every build and every fix.

  • security-auditreads

    Security, dependency and secrets audits of a repository.

  • releasereads

    Release readiness, blockers, proposed version and draft notes.

Raise your own crew

You need Orca and a coding agent it can run. The crew comes set up for Claude Code, and works with any agent Orca supports for bots, such as Codex, Cursor, GitHub Copilot or Gemini CLI. It runs on your own plan with that provider.

  1. Turn on orchestration

    In Orca, open Settings, then Experimental, and enable orchestration.

  2. Create the captain

    Clone the repository. In the Bots section of Orca, create one bot named Orcastrator [LEAD] with your agent.

  3. Give it its soul and skill

    From the repository, copy Orcastrator's identity and the pipeline skill into its home. Using an agent other than Claude Code? Set it in skills/kds-pipeline/agent.yaml first.

    scripts/install.sh orcastrator

    Run it after the new bot has written its first message in its chat, so Orca's first-run setup doesn't overwrite what you install.

  4. Onboard a project

    Ask Orcastrator to onboard one of your Orca projects. It will ask for Chartbeard: create it from the card it shows, wait for its first message, run scripts/install.sh chartbeard, and Chartbeard writes the project's profile on a branch. Check every command in that profile, then tell Orcastrator to merge it.

  5. Give the captain a job

    Tell Orcastrator what you need: a feature, a bug, a review. It writes the brief and hands it to the crew, asking for each bot the first time it needs one.
